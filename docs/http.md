# HTTP: конспект

## 1. Как это работает

HTTP это протокол «запрос — ответ». Клиент (браузер, `curl`, скрипт на `httpx`) отправляет запрос на сервер, сервер возвращает ответ. Каждая пара запрос и ответ независима: по умолчанию сервер не помнит предыдущие запросы (протокол stateless). Поэтому всё, что нужно для работы (например, авторизация), клиент передаёт в каждом запросе: токеном или cookie.

## 2. Запрос

Запрос состоит из четырёх частей:

1. стартовая строка: метод, путь, версия протокола;
2. заголовки;
3. пустая строка;
4. тело (необязательно, у GET обычно его нет).

Мой запрос из практики:

```
curl.exe -i -X POST https://jsonplaceholder.typicode.com/posts -H "Content-Type: application/json" -d "@data.json"
```

| Часть команды | Что означает |
|---|---|
| `-X POST` | метод запроса |
| `https://jsonplaceholder.typicode.com/posts` | адрес: хост и путь к ресурсу |
| `-H "Content-Type: application/json"` | заголовок: сообщает серверу, что тело в формате JSON |
| `-d "@data.json"` | тело запроса берётся из файла `data.json` |
| `-i` | показать заголовки ответа |

Так запрос выглядит на проводе (упрощённо, `curl` добавляет ещё несколько заголовков):

```
POST /posts HTTP/1.1
Host: jsonplaceholder.typicode.com
Content-Type: application/json

{"title": "test", "body": "hello", "userId": 1}
```

## 3. Ответ

Ответ тоже состоит из четырёх частей: стартовая строка (версия, **код статуса**, пояснение), заголовки, пустая строка, тело.

Ответ сервера на мой POST (сокращённо):

```
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: https://jsonplaceholder.typicode.com/posts/101

{"title": "test", "body": "hello", "userId": 1, "id": 101}
```

- **`201 Created`**: ресурс создан.
- **`Content-Type`**: формат тела, чтобы клиент знал, как его разбирать (здесь JSON).
- **`Location`**: адрес только что созданного ресурса.
- **`"id": 101`**: идентификатор присвоил сервер.

Важное замечание: `jsonplaceholder` это тестовый сервис, он ничего не сохраняет. `GET /posts/101` после такого POST вернёт 404, хотя ответ был 201.

## 4. Методы

| Метод | Что делает | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | получает ресурс | да | да |
| POST | создаёт ресурс или запускает действие | нет | нет |
| PUT | заменяет ресурс целиком | нет | да |
| PATCH | меняет часть ресурса | нет | нет (не гарантируется) |
| DELETE | удаляет ресурс | нет | да |

Определения:

- **Безопасный метод** не меняет состояние сервера (только чтение).
- **Идемпотентный метод**: повтор того же запроса оставляет сервер в том же состоянии, что и один запрос.

Примеры:

- `PUT /users/1` с теми же данными десять раз: остаётся один пользователь с одними и теми же данными. Идемпотентен.
- `POST /orders` десять раз: десять заказов. Не идемпотентен.
- `DELETE /users/1`: первый раз 200 или 204, дальше 404, но состояние одно и то же (пользователя нет). Идемпотентность считается по состоянию сервера, а не по коду ответа.
- `PATCH` вида «увеличить счётчик на 1» не идемпотентен: каждый вызов меняет результат.

Как запомнить:

- **Безопасные**: GET, HEAD, OPTIONS, TRACE.
- **Идемпотентные**: безопасные, плюс PUT и DELETE.
- **Остальные** (POST, PATCH, CONNECT) не идемпотентны.

## 5. Коды ответа

Первая цифра задаёт класс: **4xx**: ошибка на стороне клиента (нужно исправить запрос), **5xx**: ошибка на стороне сервера (повтор позже может помочь).

| Код | Название | Когда приходит |
|---|---|---|
| 200 | OK | запрос выполнен, результат в теле |
| 201 | Created | ресурс создан (обычно ответ на POST), адрес в `Location` |
| 204 | No Content | выполнено, тела в ответе нет (часто для DELETE) |
| 301 | Moved Permanently | ресурс переехал навсегда, новый адрес в `Location` |
| 304 | Not Modified | версия в кеше клиента актуальна (работает с `ETag`) |
| 400 | Bad Request | запрос некорректен, например сломан JSON |
| 401 | Unauthorized | не аутентифицирован: нет токена или он неверный («кто ты?») |
| 403 | Forbidden | аутентифицирован, но прав нет («знаю, кто ты, но нельзя») |
| 404 | Not Found | ресурса нет (мой запрос `/todos/99999`) |
| 409 | Conflict | конфликт с текущим состоянием, например email уже занят |
| 422 | Unprocessable Entity | запрос разобран, но данные не проходят валидацию; FastAPI возвращает его при ошибке Pydantic |
| 500 | Internal Server Error | ошибка в коде сервера |
| 502 | Bad Gateway | шлюз получил плохой ответ от вышестоящего сервера |
| 503 | Service Unavailable | сервис временно недоступен |

## 6. Заголовки, которые встретил

- **`Content-Type`**: формат тела (`application/json`).
- **`Location`**: адрес созданного (201) или перенесённого (3xx) ресурса.
- **`Cache-Control`**: правила кеширования. `max-age=43200` значит «можно хранить 12 часов». В моей практике даже ответ 404 пришёл из кеша (был заголовок `Age`).
- **`ETag`**: идентификатор версии ресурса. Клиент присылает его в `If-None-Match`, и если ресурс не менялся, сервер отвечает `304`.
- **`Authorization`**: сюда клиент кладёт токен (пригодится в части про авторизацию).

## 7. Практика

Скрипт [`http_client.py`](../fastapi-learning/http_client.py) делает GET и POST через `httpx`, вызывает `raise_for_status()` и обрабатывает три вида ошибок:

| Исключение | Когда возникает | Есть ли `response` |
|---|---|---|
| `httpx.HTTPStatusError` | сервер ответил кодом 4xx или 5xx | да (`e.response.status_code`) |
| `httpx.TimeoutException` | сервер не ответил за `TIMEOUT` | нет |
| `httpx.RequestError` | нет соединения, ошибка DNS | нет |

Проверенные случаи: успех (200), несуществующий ресурс (404), создание (201), таймаут, отключённая сеть. Главный вывод: ответ существует только тогда, когда сервер ответил, поэтому `.response` нельзя читать у таймаута и ошибок соединения.
